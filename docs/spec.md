# Personal Website — Spec

## Goals
- Single-page React SPA, minimal aesthetic, blog/writing-leaning content.
- TypeScript + Bun for all local tooling (package manager, dev server, bundler, tests).
- Static deploy to Cloudflare today; **same project** grows into dynamic routes via Workers without restructuring.

## Stack
| Concern | Choice | Why |
|---|---|---|
| Language | TypeScript (strict) | Per requirement |
| Local tooling | Bun | Per requirement & CLAUDE.md |
| UI | React 19 | Mainstream, easy to grow |
| Styling | Tailwind CSS v4 | Minimal config, utility-first |

| Deploy CLI | Wrangler | Cloudflare's deploy/dev tool |

## Deployment model
- **Local dev:** `Bun.serve` + HMR, per CLAUDE.md. Fast inner loop.
- **Pre-deploy check:** `wrangler dev` runs the same Worker runtime Cloudflare runs in prod, so you can sanity-check static SPA behavior and any future Worker code locally.
- **Build:** `bun run build` → invokes `scripts/build.ts`, which calls `Bun.build()` on `src/index.html` and then copies `public/` → `dist/`. Bun's HTML bundler only emits files reachable from the HTML/CSS/JS import graph, so the `public/` copy step is required for unreferenced static assets like `robots.txt`.
- **Deploy:** `wrangler deploy` uploads `dist/` to Workers Static Assets. Or wire GitHub → Cloudflare for git-triggered builds (Cloudflare build image has Bun preinstalled).
- **Custom domain:** add `moster.dev` via Cloudflare dashboard; SSL/HTTPS automatic.

### Why Workers + Static Assets, not Pages
As of 2026, Cloudflare officially recommends Workers + Static Assets over Pages for new projects. Pages isn't deprecated, but Workers now has full feature parity for static hosting plus a unified config that handles static assets, dynamic routes, cron, KV, and bindings in one `wrangler.toml`. The migration guide explicitly tells new projects to skip Pages.

Two reasons specific to this project:
1. **"Easy switch to dynamic later"** is materially cleaner here — same project, same `wrangler.toml`, same deploy command. With Pages you'd be adding a separate "Functions" concept; with Workers it's one fetch handler already stubbed.
2. **Future-proof:** Cloudflare is steering new projects to Workers; Pages may stay supported but it's the legacy path.

### Free tier (relevant to this project)
- Unlimited bandwidth, unlimited static-asset requests (no credit card required)
- 100,000 dynamic Worker requests/day (only counts when server-side code is added)
- Workers Builds (Git integration) free tier: **3,000 build minutes/month**, 1 concurrent build, 20-min timeout per build, 2 vCPU / 8 GB RAM / 20 GB disk per builder. Local `wrangler deploy` doesn't count against this.
- 20,000-file limit per deployment
- Custom domain + automatic HTTPS included

### Tradeoff vs Vercel
Dynamic code on Workers is a `fetch` handler in the Workers V8 runtime, **not** a `Bun.serve` server. Bun is still used for dev/build/test locally (matching CLAUDE.md). Upside: one deployment, no static-vs-functions split, generous free tier.

### `wrangler.toml` (static-only, day 1)
```toml
name = "personal-site"
main = "src/worker.ts"
compatibility_date = "2026-05-17"

[assets]
directory = "./dist"
binding = "ASSETS"
not_found_handling = "single-page-application"  # serves index.html for unknown paths → SPA routes work

[vars]
# env vars here later

# When you add a Worker fetch handler (forms, API, OG images), uncomment:
# [[routes]]
# pattern = "moster.dev/api/*"
# zone_name = "moster.dev"
```

### `src/worker.ts` (pass-through stub)
```ts
export default {
  async fetch(req: Request, env: Env): Promise<Response> {
    return env.ASSETS.fetch(req);
  },
} satisfies ExportedHandler<Env>;
```
Costs nothing (asset requests are free) and gives a one-line place to intercept later — e.g., add `/api/contact` without touching deployment shape.

The `Env`, `ExportedHandler`, and `Fetcher` types come from `worker-configuration.d.ts`, which is **generated by `wrangler types`** from `wrangler.toml`. Run `bunx wrangler types` after any binding change (it should be part of `bun run check` and CI). The generated file is gitignored. See the tsconfig changes in the "Existing files — handling" table below.

### `scripts/build.ts` (programmatic build + public/ copy)
```ts
import { cp, rm } from "node:fs/promises";

await rm("dist", { recursive: true, force: true });

const result = await Bun.build({
  entrypoints: ["src/index.html"],
  outdir: "dist",
  minify: true,
  sourcemap: "linked",
});

if (!result.success) {
  for (const log of result.logs) console.error(log);
  process.exit(1);
}

await cp("public", "dist", { recursive: true });
```
The explicit `cp("public", "dist", …)` step exists because Bun's HTML bundler does not auto-copy a `public/` directory — it only emits files in the import graph.

## Single-page content (v1)
One vertical scroll, anchor links in a sticky/minimal nav:
1. **Hero** — name, one-line bio, primary links.
   - Copy (verbatim, "my pleasure" must be preserved): *"Hi, I'm Jalo and I'm a Software Engineer at Chick-fil-A. It's my pleasure to invite you into my portfolio."*
   - Links:
     - GitHub → `https://github.com/jlvmoster`
     - Instagram → `https://instagram.com/jlvmoster`
     - LinkedIn → `https://linkedin.com/in/jlvmoster`
2. **Writing** — empty state for now ("first post coming soon"), placeholder for post list.
3. **About** — short paragraph, current focus, location.
4. **Contact** — `mailto:` link initially; later swappable for a form posting to `/api/contact`.

Each section is its own component so future expansion (e.g., promoting "Writing" to its own route) is a lift-and-shift.

## Styling system
- Tailwind v4 with CSS variables for the few tokens we have: `--bg`, `--fg`, `--muted`, `--accent`, `--font-sans`, `--font-serif`.
- Light + dark via `prefers-color-scheme`, no toggle yet.
- Typography: system stack
  - Sans: `ui-sans-serif, system-ui, -apple-system, "Segoe UI", Roboto, "Helvetica Neue", Arial, sans-serif`
  - Serif (long-form prose later): `ui-serif, Georgia, Cambria, "Times New Roman", serif`
  - Mono: `ui-monospace, SFMono-Regular, "SF Mono", Menlo, monospace`
- Spacing: generous line-height, max-width ~65ch on prose blocks.
- No component libraries — keep the surface area small.

## Dev workflow
```
bun install
bun run dev          # scripts/dev.ts — Bun.serve, HMR
bun run build        # bun build → dist/
bun run preview      # wrangler dev — exercise Workers runtime locally
bun run deploy       # wrangler deploy
bun test
bun run check        # biome + tsc --noEmit
```
GitHub Action (or Cloudflare Git integration): `bun install && bun run build && bunx wrangler deploy` on push to `master`.

## Growth path (designed-in, not built)
- **Blog with MDX:** posts in `src/content/`, generate route per file at build, prerender to static HTML in `dist/`. Add React Router. No deploy change.
- **Contact form / newsletter:** extend `src/worker.ts` with an `/api/contact` branch using Resend or Loops. Same deploy, no new service. Stays in free tier until 100K req/day.
- **OG images:** add a `/api/og` branch using `workers-og`. Same deploy.
- **CMS later:** Tina or markdown-via-PR. Deferred.
- **Analytics:** Cloudflare Web Analytics (free, privacy-friendly, one snippet).
- **Edge data:** Workers KV / D1 / R2 available in the same `wrangler.toml` if needed.

## Out of scope for v1
Auth, database, comments, search, RSS, i18n, custom font hosting, theme toggle. Each has a clean place to land later.
